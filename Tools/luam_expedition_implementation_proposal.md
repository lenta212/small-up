# LuaM Expedition Implementation Proposal

Статус: предложение следующего цикла разработки<br>
Дата: 2026-07-13<br>
Основание: `Tools/luam_expedition_worldgen_design.md`

## Фактически выполнено в первом срезе

- добавлен server-only `LuaMExpeditionPlan` без `EntityUid`;
- добавлены детерминированные макрорегионы, шесть POI и обязательные маршруты;
- добавлены валидатор границ/связности/уникальности и стабильный `PlanHash`;
- добавлены NUnit-тесты для одинакового seed/version и размеров `64x64`, `513x257`, `512x512`;
- профиль персонажа больше не удаляется физически: строка помечается через `is_archived`/`archived_at`, получает `slot = NULL` и скрывается из активных preferences;
- добавлен серверный `GetCharacterIdAsync`, возвращающий `Profile.Id` активного слота для будущей прогрессии;
- обычное создание в освобождённом слоте выдаёт новый `Profile.Id`, а старый профиль возвращается только через явный серверный `RestoreArchivedCharacterAsync`;
- добавлены SQLite/PostgreSQL миграции и EF snapshot-поля;
- добавлена серверная команда `luam_expedition_plan` для проверки seed/version без передачи полного плана клиенту;
- интеграционно проверены planner, новая личность после повторного использования слота, явное идемпотентное восстановление архивного `Profile.Id` и отсутствие pending model changes.

Пока не подключено к игровому ECS: `ExpeditionDirector`, чанковая материализация поверхности, delta/snapshot экспедиции и отдельные таблицы XP/скилов остаются следующими этапами.

## 1. Предложение

Следующим крупным направлением реализовать серверный `ExpeditionDirector`, который связывает существующие `SalvageSystem`, `BiomeSystem`, `DungeonSystem` и Frontier worldgen через детерминированный макроплан и долговременное хранилище изменений.

Не начинать с контента десятков биомов и комнат. Первый результат должен доказать четыре свойства:

1. большая поверхность загружается и выгружается чанками;
2. обязательная миссия всегда проходима;
3. открытая экспедиция переживает рестарт без изменения и дюпа;
4. персонаж и его прогресс переживают рестарт, технический раунд и недельную смену;
5. скрытый план отсутствует в клиентской сборке.

## 2. Первый вертикальный срез

Создать одну тестовую экспедицию `LuaMExpeditionPrototype`:

- виртуальная поверхность `512x512` тайлов;
- один основной биом и один вложенный подбиом;
- точка высадки;
- три POI: обязательная лаборатория, дополнительная шахта и точка эвакуации;
- один ограниченный dungeon внутри лаборатории;
- связный маршрут между обязательными точками;
- сохранение изменённых тайлов, открытых контейнеров и tombstones лута;
- восстановление после штатного рестарта и аварийного завершения;
- сохранение стабильного `Profile.Id` персонажа при техническом раунде и рестарте;
- удаление одноразовой экспедиции либо сохранение закреплённой маяком.

Размер `512x512` относится к виртуальным координатам. Вся площадь не должна одновременно заполняться ECS-сущностями.

## 4. Предлагаемая модель хранения

Это логическая модель, не окончательные имена таблиц:

| Запись | Назначение |
|---|---|
| `ExpeditionManifest` | `ExpeditionId`, `CampaignId`, seed, generator version, plan hash, статус и policy сохранения |
| `ExpeditionRegion` | координаты, biome/scenario, discovered, depleted, edge contracts и revision |
| `ExpeditionSite` | стабильный `SiteId`, prototype/tag, footprint, unique scope, состояние цели |
| `ExpeditionChunkDelta` | изменённые тайлы, декали и компактный журнал изменений |
| `ExpeditionEntitySnapshot` | значимые построенные, перемещённые или изменённые сущности |
| `ExpeditionTombstone` | удалённые процедурные сущности, забранный лут и завершённые одноразовые события |
| `ExpeditionCheckpoint` | атомарная отметка согласованного snapshot/delta revision |

Персонаж не хранится внутри `ExpeditionManifest`. Экспедиция содержит только ссылку на стабильный `Profile.Id`/`CharacterId`. Внешний вид и слот остаются в preferences, а карьерная прогрессия, параметры, навыки, крио-состояние и хроника должны иметь отдельные серверные записи с `ON DELETE RESTRICT`.

Обязательные свойства БД:

- уникальность `(ExpeditionId, SiteId)`;
- уникальность источника изменения для идемпотентного повторения;
- optimistic revision или транзакционная блокировка на запись региона;
- soft archive вместо физического удаления активного недельного мира;
- миграция формата снапшота с карантином неизвестной версии;
- одинаковая поддержка SQLite для тестов и PostgreSQL для production.

## 5. Этапы реализации

### Этап 0. Baseline и профилирование

Работы:

- добавить benchmark-сценарий быстрого перемещения по BiomeSystem;
- измерить число загруженных чанков, сущностей, тайлов, сетевой трафик и длительность server tick;
- воспроизвести хвост выгрузки одного чанка раз в десять секунд;
- измерить текущую генерацию dungeon `128x128` и `272x272`;
- зафиксировать memory/tick baseline для 1, 5, 10 и 20 игроков, разделённых на группы.

Критерий готовности: результаты сохранены, определён безопасный active radius и подтверждено, какие текущие узкие места исправляются до прототипа.

### Этап 1. Чистый детерминированный planner

Работы:

- определить `ExpeditionId`, `GeneratorVersion`, `PlanHash` и derivation дочерних seed;
- генерировать макрорегионы без `EntityManager`;
- разместить Entry, Objective, Extraction и вторичные POI;
- построить MST с дополнительными петлями;
- записать edge contracts;
- добавить validator связности, footprint и уникальности;
- сортировать все коллекции перед случайным выбором.

Критерий готовности: тысячи seed проходят property tests, а Windows/Linux создают одинаковый `PlanHash`.

### Этап 2. Потоковая поверхность

Работы:

- связать `RegionPlan` с существующими biome layers;
- исправить выгрузку BiomeSystem на time-budgeted batch вместо одного чанка за интервал;
- добавить explicit chunk pins для активной цели, gateway и закреплённых объектов;
- запретить локальной генерации менять зарезервированный footprint POI;
- добавить метрики loaded/pending/modified chunks.

Критерий готовности: быстрое перемещение не создаёт неограниченный хвост чанков, а края дорог и биомов совпадают после повторной загрузки.

### Этап 3. POI и миссия

Работы:

- расширить atlas-комнаты метаданными портов, веса, сложности и unique scope;
- создавать ограниченный dungeon внутри footprint;
- гарантировать соединение обязательных портов weighted A*;
- добавить связанный scenario tag для геометрии, NPC и задачи;
- использовать `SalvageSystem` для предложения, FTL, статуса и награды.

Критерий готовности: любой принятый seed имеет достижимые Entry, Objective и Extraction; обязательный POI создаётся один раз.

### Этап 4. Персистентность и рестарт

Работы:

- добавить manifest, region/site state, delta, snapshot и tombstone;
- сохранять checkpoint перед выгрузкой и shutdown;
- восстанавливать карту без повторной выдачи лута;
- поддержать crash recovery незавершённого checkpoint;
- компактировать длинные журналы дельт;
- хранить пользовательские корабли/сложные гриды полным снапшотом.

Критерий готовности: штатный рестарт и принудительное завершение процесса не меняют открытую геометрию, не теряют постройки и не создают дубликаты.

### Этап 4a. Персонаж вне рестартов и раундов

Работы:

- считать `Profile.Id` стабильным `CharacterId` внутри серверной прогрессии;
- не удалять строки профилей физически: использовать `is_archived` и `archived_at`;
- сохранять карьерный XP, параметры, навыки, достижения, крио-состояние и хронику по `Profile.Id`;
- привязывать недельный зачёт к `CampaignShiftId`, а не к техническому `RoundId`;
- писать checkpoint прогрессии при подтверждённом событии, конце раунда, shutdown и периодически;
- добавить уникальность выплаты `(CampaignShiftId, ProfileId, SourceType, SourceInstanceId, AwardCode)`;
- восстановление после crash должно быть идемпотентным и не создавать дубликат тела, XP или награды.

Критерий готовности: два рестарта и несколько новых `RoundId` не меняют `Profile.Id`, общий XP, навыки, параметры и состояние крио; удаление слота только скрывает профиль, но не удаляет его историю.

### Этап 5. ExpeditionDirector и жизненный цикл

Работы:

- состояния `Discovered`, `Provisioning`, `Active`, `Dormant`, `Depleted`, `Archived`, `Quarantined`;
- сигнал, сканирование, контракт, высадка и эвакуация;
- политики `Ephemeral`, `BeaconPreserved`, `CampaignPermanent`;
- выгруженная симуляция только агрегированными таймерами;
- админ-команды inspect/rebuild/quarantine без раскрытия плана обычному клиенту.

Критерий готовности: одноразовая экспедиция удаляется после безопасного grace period, закреплённая возвращается после рестарта, а недельная архивируется только явным переходом состояния.

### Этап 6. Новые генераторы содержимого

Порядок:

1. открытая планета: layered noise и overmap specials;
2. пещера: обязательный path spine плюс cellular/Voronoi mask;
3. мегаструктура: mission graph, BSP/prefabs и несколько этажей;
4. космические сигналы и дрейфующие локации;
5. WFC только как ограниченный внутренний слой;
6. более дорогие реки, эрозия и геология после профилирования.

Критерий готовности: каждый профиль использует общий plan/persistence contract и не создаёт собственное несовместимое хранилище.

## 6. Обязательные тесты

### Детерминизм

- одинаковый seed/version создаёт одинаковый plan hash;
- перестановка порядка исходных словарей не меняет результат;
- сохранённая старая generator version не использует новые правила молча.

### Связность

- существует маршрут `Entry -> Objective -> Extraction`;
- обязательные POI ports соединены;
- дороги, реки и тоннели совпадают на границах регионов;
- лут и цели не размещаются в недостижимых компонентах.

### Персистентность

- tile/entity delta переживает рестарт;
- `Profile.Id`, карьерный XP и навыки переживают рестарт и новый `RoundId`;
- архивирование слота сохраняет профиль и связанные записи;
- повтор одного `SourceInstanceId` не выдаёт вторую выплату;
- открытый контейнер остаётся открытым;
- забранный предмет не появляется повторно;
- уничтоженный уникальный NPC не возрождается из базового seed;
- повтор checkpoint остаётся идемпотентным;
- неизвестная snapshot version переводит регион в quarantine.

### Производительность

- planner не создаёт ECS-сущности;
- применение dungeon сохраняет текущий time-sliced подход;
- загруженные чанки сходятся к ожидаемому active set после быстрого перемещения;
- разделение игроков на несколько групп не вызывает неограниченного роста памяти;
- серверный tick не получает длинную синхронную генерацию.

### Клиентская поверхность

- клиентский ZIP не содержит planner, seed, закрытые каталоги POI и таблицы наград;
- безопасный DTO не раскрывает неоткрытые координаты;
- клиент не может подтвердить завершение цели или размер награды;
- release audit падает при появлении server-only canary в клиентском пакете.

## 7. Основные риски и меры

| Риск | Мера |
|---|---|
| атмосфера и электросети удерживают регион активным | отдельные этажи/MapId, explicit pins, снапшот сложного грида |
| быстрый транспорт создаёт хвост чанков | time-budgeted batch unload и лимит pending queue |
| обновление генератора меняет мир | generator version, plan hash и сохранённые site manifests |
| дюп после сбоя | tombstones, source id и атомарный checkpoint |
| POI пересекает границу чанка | footprint и edge contracts создаются до микрогенерации |
| плохой seed блокирует миссию | validation, retry с derived attempt seed, сохранение принятого plan hash |
| полный план попадает клиенту | только `Content.Server`, package audit и безопасные DTO |
| стоимость сохранения растёт всю неделю | delta compaction, snapshots и retention для архивов |
| несколько групп одновременно меняют регион | region revision/lease и транзакционная запись |

## 8. Решения, которые нужно принять после этапа 0

1. Размер макрорегиона: `64x64` или `128x128`.
2. Active radius поверхности для одной группы.
3. Максимальное число одновременно materialized POI.
4. Порог delta compaction.
5. Какие типы сущностей сохраняются дельтой, а какие полным снапшотом.
6. Допустима ли постройка произвольных атмосферных баз на поверхности первой версии.
7. Срок жизни `Ephemeral`-экспедиции после ухода последнего игрока.

Эти значения нельзя назначать по ощущениям; они принимаются по baseline и crash/restart тестам.

## 9. Рекомендуемая ближайшая задача

Начать с этапов 0 и 1 одним изолированным изменением:

1. benchmark текущей чанковой загрузки и выгрузки;
2. server-only модели `ExpeditionPlan`;
3. детерминированный planner без ECS;
4. генерация Entry, Objective, Extraction и трёх POI;
5. connectivity/uniqueness validator;
6. `PlanHash` и property tests на большом наборе seed;
7. диагностическая server-only команда, печатающая краткую сводку плана без его передачи клиенту.

Этот срез не требует сразу менять боевой Salvage или БД. Он создаёт проверяемый фундамент, после которого можно отдельно подключать streaming, POI и персистентность.

## 10. Условие начала production-разработки

Предложение считается принятым, когда согласованы:

- архитектура `ExpeditionPlan` и server-only граница;
- первый профиль открытой планеты;
- измеримые лимиты active set;
- обязательность рестарт-персистентности до публичного запуска;
- политика лицензий: собственная реализация алгоритмов и отдельная проверка любого переносимого кода/ассета.

После этого первая кодовая задача — детерминированный planner и его property tests, а не рисование контента.
